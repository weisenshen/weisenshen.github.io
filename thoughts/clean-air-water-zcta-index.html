Clean Air, Clean Water, and the ZIP Code Problem

Clean air and clean water are easy to praise and hard to measure well. The hard part is not the slogan. The hard part is geography, data gaps, and the fact that missing data is not the same thing as safety.

I am thinking about a small, modular Python project that ranks U.S. ZIP Code Tabulation Areas, or ZCTAs, by air and water quality. Not USPS ZIP codes. Census ZCTAs. Close enough to be useful for public reasoning; precise enough to avoid pretending that postal routes are environmental units.

The project should live outside my Antarctica plotting work, probably at: /Users/weisenshen/Work/us-zcta-environmental-index.

The basic idea

Start with geography. Download Census TIGER/Line ZCTA shapefiles, preserve the polygon geometry, calculate centroids, and keep Census internal points. Every later data join depends on getting this part right.

Then add air. EPA AirData provides PM2.5 and ozone measurements from monitors. Those monitors do not sit inside every ZCTA, so the pipeline needs nearest-monitor mapping or inverse distance weighting. Approximation is allowed. Silent approximation is not.

Then add water. EPA drinking-water data is harder because public water systems do not map cleanly onto ZCTAs. Public Water System IDs need to be connected to service areas and ZIP/ZCTA geographies where possible. Areas likely served by private wells, or areas with insufficient public data, need to be flagged explicitly.

Scoring without lying

A 0-100 index is useful only if it keeps its caveats visible. Air and water metrics can be normalized with min-max scaling and combined with transparent weights. But every score should carry data-quality flags:

  • missing air data
  • missing water data
  • likely private-well areas
  • low-confidence spatial assignments

A place with no water-system record is not automatically clean. Sometimes the silence is the signal.

Phase 1

The first implementation phase should be boring on purpose:

  1. Download the Census TIGER/Line ZCTA shapefile.
  2. Validate the ZIP archive and required columns.
  3. Load polygons with GeoPandas.
  4. Calculate centroids in a projected CRS.
  5. Export a GeoPackage and a centroid CSV.

The derived table should include clean ZCTA codes, projected centroid longitude and latitude, Census internal-point coordinates, and land and water area in square kilometers.

Working rules

Build one phase at a time. Explain input schemas before writing code. Use modular Python. Handle download failures, missing columns, empty datasets, invalid geometry, CRS mistakes, and missing metric values explicitly.

Preferred tools are familiar: pandas, geopandas, requests, scikit-learn, shapely, and pyproj.

GitHub should hold code, schemas, documentation, tests, and small reference files. It should not hold Census shapefiles, EPA raw downloads, GeoPackages, large processed datasets, or generated outputs.

This is the kind of project I like: concrete enough to build, messy enough to be real, and public enough that the assumptions should not hide in the footnotes.
